## 1. 背景：認証アーキテクチャの全体像

### 1.1 システム構成と認証の関係

```
┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
│  マイアプリ          │   │  マイページ　　      │   │  CMS管理画面         │
└────────┬────────────┘   └────────┬────────────┘   └────────┬────────────┘
         │                         │                          │
    JWT (RS256)            Session/Cookie              JWT (HS256)
         │                         │                          │
         ▼                         ▼                          ▼
┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
│  CMS API            │   │  マイページ API      │   │  CMS API            │
│  公開鍵で JWT 検証   │   │  Token 署名・発行    │   │  共通鍵で JWT       │
│  + HS256 で管理画面  │   │  (認証の中心)        │   │  署名・検証         │
│    Token 署名・検証  │   │                      │   │                     │
└─────────────────────┘   └──────────────────────┘   └─────────────────────┘
```

**ポイント**: マイページ API が Mobile App の認証中心であり、CMS API は 2 つの役割を持つ:

1. Mobile App からのリクエスト → マイページ API が署名した JWT を**公開鍵で検証**
2. CMS 管理画面からのリクエスト → CMS API 自身が HS256 で**署名・検証を完結**

### 1.2 Token の種類と役割

| Token             | 形式           | 発行者         | 有効期限 | 自己完結？ | 用途                                  |
| ----------------- | -------------- | -------------- | -------- | ---------- | ------------------------------------- |
| Access Token      | JWT (RS256)    | マイページ API | 1 時間   | ✅ はい    | App → CMS API / マイページ API 認証   |
| Refresh Token     | ランダム文字列 | マイページ API | 24 時間  | ❌ いいえ  | Access Token の再取得                 |
| tempToken         | UUID           | マイページ API | 30 秒    | ❌ いいえ  | WebView ログイン → JWT 交換の中間凭証 |
| SSO Ticket        | UUID           | マイページ API | 30 秒    | ❌ いいえ  | App → マイページ Web の SSO 用        |
| CMS Access Token  | JWT (HS256)    | CMS API        | 30 分    | ✅ はい    | CMS 管理画面 → CMS API 認証           |
| CMS Refresh Token | ランダム文字列 | CMS API        | 8 時間   | ❌ いいえ  | CMS Access Token の再取得             |

**「自己完結」の意味**: JWT は Payload にユーザー情報を含むため、サーバー側で DB を照会せずに検証できる。UUID 系の Token は単なるランダム文字列であり、サーバー側の DB/Redis にある対応レコードを照会しなければユーザーを特定できない。

### 2.2 生体認証ログイン（再ログイン）

生体認証データ（指紋・顔）は OS の安全ハードウェア（Secure Enclave / TEE）にのみ保存され、サーバーには一切送信されない。App はこのデータに直接アクセスできず、OS に「ユーザーを検証してください」とリクエストするのみ。

```
ユーザー               App                  Keychain/Keystore (OS)    マイページ API
  │                     │                        │                        │
  │  App を起動          │                        │                        │
  ├────────────────────►│                        │                        │
  │                     │  Keychain に Token あり？│                        │
  │                     ├───────────────────────►│                        │
  │                     │  あり（生体認証保護下） │                        │
  │                     │◄───────────────────────┤                        │
  │                     │                        │                        │
  │  ┌────────────────────────────────┐          │                        │
  │  │ 🔐 Face ID / 指紋で認証       │          │                        │
  │  │    してください                │          │                        │
  │  └────────────────────────────────┘          │                        │
  │  顔 / 指紋をかざす  │                        │                        │
  ├────────────────────►│                        │                        │
  │                     │  OS が生体検証 ✓        │                        │
  │                     │  → Keychain ロック解除  │                        │

  │                     │◄───────────────────────┤                        │
  │                     │                        │                        │
  │                     │  ---- Token が有効な場合 ----                    │
  │                     │  Access Token 有効期限チェック                    │
  │                     │  → 有効 → そのまま使用                           │
  │                     │  → 期限切れ → POST /api/auth/refresh             │
  │                     │     { refreshToken: RT }                         │
  │                     ├─────────────────────────────────────────────────►│
  │                     │                             新 AT + 新 RT        │
  │                     │◄─────────────────────────────────────────────────┤
  │                     │                                                  │
  │                     │  ---- Refresh Token も期限切れの場合 ----         │
  │                     │  401 エラー → WebView ログイン画面に遷移         │
```

**重要**: マイページ API は生体認証の存在を一切認識しない。受信するのは通常の JWT リフレッシュリクエストのみ。

#### 現行設計の制約と Device Token（オプション拡張）

> ⚡ **本項はオプション機能**です。マイページ API 側の追加開発予算が必要ですが、UX を大幅に改善します。予算が確保できない場合は、上記の現行設計（RT 失効後に WebView 再ログイン）で問題なく運用可能です。

現行設計では Refresh Token（24h）が切れると、ユーザーは WebView で ID/PW を再入力する必要がある。**Device Token** を導入すると、RT 失効後も生体認証だけで再ログインでき、ID/PW の入力頻度を大幅に削減できる。

| 項目                   | 現行設計（Device Token なし） | オプション（Device Token あり）          |
| ---------------------- | ----------------------------- | ---------------------------------------- |
| **RT 失効後の挙動**    | WebView で ID/PW 再入力       | 生体認証のみで再ログイン                 |
| **ID/PW 入力頻度**     | 最悪 24 時間ごと              | 最悪 90 日ごと                           |
| **PW 変更の影響**      | 即座に再ログイン必要          | Device Token は独立して有効（PW 非依存） |
| **マイページ追加開発** | なし                          | API 1 本 + DB テーブル 1 つ              |

**Token 階層イメージ**:

```
Device Token（90 日）── 生体認証で取り出し → 新 AT + RT を再発行
  └─ Refresh Token（24h）── 自動更新
       └─ Access Token（1h）── 毎回の API 認証
```

**RT 失効後の再ログインフロー（Device Token あり）**:

```
ユーザー               App                  Keychain            マイページ API
  │  App 起動            │                      │                    │
  ├─────────────────────►│  AT+RT 期限切れ       │                    │
  │                      │                      │                    │
  │  🔐 生体認証          │                      │                    │
  ├─────────────────────►│  Device Token 取得    │                    │
  │                      ├─────────────────────►│                    │
  │                      │  { deviceToken }      │                    │
  │                      │◄─────────────────────┤                    │
  │                      │                      │                    │
  │                      │  POST /api/auth/device-reauth              │
  │                      │  { deviceToken: "DT-xxx" }                 │
  │                      ├───────────────────────────────────────────►│
  │                      │              DT 検証 ✓ → 新 AT + 新 RT     │
  │                      │◄───────────────────────────────────────────┤
  │  ホーム画面           │                      │                    │
  │◄─────────────────────┤                      │                    │
```

**無効化シーン**: 全デバイスログアウト / アカウント無効化 / セキュリティ異常 → Device Token 無効化。パスワード変更は**影響なし**。90 日経過で自然失効し、WebView 再ログインが必要。

### 2.3 SSO 連携（App → マイページ Web）

App にログイン済みのユーザーが外部ブラウザでマイページ Web を開く際、パスワード再入力なしでログインする仕組み。

```
React Native App          マイページ API          マイページ DB        外部ブラウザ
     │                         │                      │                   │
     │ ※ 前提: JWT 保持済み     │                      │                   │
     │                         │                      │                   │
     │ 1. POST /api/sso/       │                      │                   │
     │    create-ticket        │                      │                   │
     │    Authorization:       │                      │                   │
     │    Bearer {JWT}         │                      │                   │
     ├────────────────────────►│                      │                   │
     │                         │ 2. JWT 検証 → user_id│                   │
     │                         │    を Payload から取得│                   │
     │                         │    Ticket(UUID) 生成  │                   │
     │                         │ 3. INSERT sso_tickets │                   │
     │                         │    (ticket, user_id,  │                   │
     │                         │     expires_at+30s)   │                   │
     │                         ├─────────────────────►│                   │
     │                         │                      │                   │
     │ 4. { ticket, url }      │                      │                   │
     │◄────────────────────────┤                      │                   │
     │                         │                      │                   │
     │ 5. 外部ブラウザ起動      │                      │                   │
     │    url?ticket=xxx       │                      │                   │
     ├────────────────────────────────────────────────────────────────────►│
     │                         │                      │                   │
     │                         │ 6. GET /sso/auth?ticket=xxx              │
     │                         │◄────────────────────────────────────────────┤
     │                         │ 7. Ticket 検証 + DELETE (ワンタイム)     │
     │                         ├─────────────────────►│                   │
     │                         │                      │                   │
     │                         │ 8. user_id で Session 生成               │
     │                         │    Set-Cookie: JSESSIONID=...            │
     │                         │    302 Redirect                          │
     │                         ├────────────────────────────────────────────►│
     │                         │                      │    マイページ表示  │
```

**Token の流れ**:

- JWT → サーバー側で user_id を取得（JWT の Payload に含まれる）
- Ticket → DB に user_id と紐付けて保存 → ブラウザからの要求時に DB から user_id を取得
- Session → ブラウザ側で Cookie として保持（App の JWT とは独立）

**JWT を直接ブラウザに渡さない理由**: URL パラメータは、ブラウザ履歴・サーバーログ・Referer ヘッダーに残るため、長寿命の JWT を URL に入れると漏洩リスクが高い。30 秒で失効するワンタイム Ticket にすることで、このリスクを最小化。

## 3. 双令牌（Access Token + Refresh Token）メカニズム

### 3.1 なぜ 2 つの Token が必要か？

Token が 1 つしかない場合のジレンマ:

| 方式                     | セキュリティ             | ユーザー体験               |
| ------------------------ | ------------------------ | -------------------------- |
| 短寿命 Token のみ（1h）  | ✅ 漏洩影響小            | ❌ 1 時間ごとに再ログイン  |
| 長寿命 Token のみ（24h） | ❌ 漏洩時に 24h 攻撃可能 | ✅ 長時間使用可能          |
| **AT（1h）+ RT（24h）**  | **✅ AT 漏洩は 1h まで** | **✅ 自動更新で 24h 使用** |

### 3.2 各 Token の役割分担

| 項目             | Access Token (AT)          | Refresh Token (RT)           |
| ---------------- | -------------------------- | ---------------------------- |
| **目的**         | API リクエストの認証       | AT の再取得                  |
| **送信頻度**     | 毎回のリクエスト（高頻度） | AT 期限切れ時のみ（低頻度）  |
| **漏洩リスク**   | 高い（送信頻度が高い）     | 低い（送信頻度が低い）       |
| **漏洩影響**     | 最大 1 時間                | Rotation で検知 + 即時無効化 |
| **格納形式**     | JWT（自己完結型）          | DB/Redis に状態保持          |
| **サーバー照会** | 不要（署名検証のみ）       | 必要（DB/Redis 照会）        |

### 3.3 動作タイムライン

```
時刻    0h        1h        2h          ...         24h
        │         │         │                        │
        ├── AT-1 ─┤         │                        │
        │  CMS API│         │                        │
        │  アクセス│         │                        │
        │         │         │                        │
        │    AT-1 期限切れ   │                        │
        │    ↓ 401 応答      │                        │
        │    ↓ Interceptor   │                        │
        │    ↓ RT-1 で更新   │                        │
        │         │         │                        │
        │         ├── AT-2 ─┤                        │
        │    Rotation:       │                        │
        │    RT-1→RT-2       │                        │
        │    (RT-1 無効化)   │                        │
        │         │         │                        │
        │         │    AT-2 期限切れ                   │
        │         │    ↓ RT-2 で更新                   │
        │         │         ├── AT-3 ─               │
        │         │    RT-2→RT-3                      │
        │         │    (RT-2 無効化)                   │
        │         │         │                        │
        │         │         │          ...           │
        │         │         │                        │
        │         │         │              RT-N 期限切れ (24h)
        │         │         │              ↓ 再ログイン必要
        │         │         │              ↓ WebView で ID/PW 再入力
```

ユーザー視点: RT は毎回のリフレッシュで新しい 24h が付与される（スライディング有効期限）ため、**24 時間以内に 1 回でも App を使えば RT は期限切れにならず、ログイン操作は一切不要**。24 時間以上 App を使わなかった場合は RT が失効し、WebView での ID/PW 再入力が必要。

> ⚡ Device Token（オプション）を導入すれば、RT 失効後も生体認証のみで復帰可能になる。詳細は 2.2 節「Device Token（オプション拡張）」を参照。

### 3.4 Refresh Token Rotation と盗難検知

```
正常な Rotation:

  RT-1 → [refresh] → AT-2 + RT-2（RT-1 は is_revoked=true に）
  RT-2 → [refresh] → AT-3 + RT-3（RT-2 は is_revoked=true に）

盗難が発生した場合:

  時点 T: 攻撃者が RT-2 を盗む
  時点 T+1: 正規ユーザーが RT-2 で更新 → RT-3 を取得（RT-2 は無効化）
  時点 T+2: 攻撃者が RT-2 で更新を試みる
            → RT-2 は is_revoked=true → ⚠ 盗難検知！
            → family_id に紐づく全 Token を即時無効化
            → 正規ユーザーも攻撃者も強制ログアウト
```

## 4. CMS API が共有 JWT で認証する仕組み

### 4.1 なぜ CMS API は独自の認証を持たないのか（Mobile App 向け）

App ユーザーのアカウントはマイページ API が管理しており、CMS API には App ユーザーの認証情報（ID/PW）がない。そのため、CMS API が独自にログイン認証を行うことは不可能。

### 4.2 RS256 による署名権限の分離

```
マイページ API                CMS API                      攻撃者
     │                          │                            │
  秘密鍵 保持 ✅               公開鍵 保持 ✅                │
     │                          │                            │
  JWT を署名 ✅                 JWT を検証 ✅                │
  JWT を検証 ✅                 JWT を署名 ❌ ← できない！    │
     │                          │                            │
                                │                            │
             CMS API が攻撃されても、                         │
             公開鍵だけでは JWT を偽造できない                │
```

### 4.3 リクエストの流れ

```
App → CMS API への全リクエスト:

GET /api/v1/contents
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyXzEyMzQ1...

CMS API の処理:
  1. Authorization ヘッダーから JWT を取出
  2. RS256 公開鍵で署名を検証 → 確かにマイページ API が署名したもの ✓
  3. Payload を解読 → { "sub": "user_12345", "exp": 1740003600 }
  4. 有効期限チェック → 未期限切れ ✓
  5. JWT ブラックリスト照会（Redis）→ 未ブラックリスト ✓
  6. 認証通過 → user_12345 としてリクエスト処理
```

### 4.4 なぜ userId を直接送信しないのか

| 方式              | 認証できる内容                     | 安全性                                                   |
| ----------------- | ---------------------------------- | -------------------------------------------------------- |
| userId を直接送信 | 「このユーザーは存在するか？」     | ❌ 偽造可能（userId は連番やメールアドレスなど推測容易） |
| JWT を送信        | 「この人は確かにログイン済みか？」 | ✅ 秘密鍵なしでは偽造不可能                              |

JWT の本質は、マイページ API による**「このユーザーは確かに認証済みです」という署名付き証明書**。

## 5. マイページ API 側の改修ポイント

マイページ API は本プロジェクト管理外の既存システムだが、Mobile App 連携のために以下の改修が必要。

### 5.1 新規 API エンドポイント

| メソッド | エンドポイント            | 用途                                | 新規/既存 |
| -------- | ------------------------- | ----------------------------------- | --------- |
| GET      | `/mobile-login`           | WebView ログインページ表示          | 新規      |
| POST     | `/api/mobile-auth/login`  | WebView ログイン処理                | 新規      |
| POST     | `/api/mobile-auth/verify` | 一時 Token 検証 → JWT 発行          | 新規      |
| POST     | `/api/auth/refresh`       | Token リフレッシュ（Rotation 対応） | 新規      |
| POST     | `/api/sso/create-ticket`  | SSO Ticket 生成                     | 新規      |

### 5.2 新規 DB テーブル

**`refresh_tokens` テーブル** — Refresh Token Rotation の状態管理用:

| カラム       | 型           | 説明                             |
| ------------ | ------------ | -------------------------------- |
| `id`         | BIGINT PK    | 主キー                           |
| `user_id`    | VARCHAR(100) | ユーザー識別子                   |
| `token_hash` | VARCHAR(64)  | SHA-256 ハッシュ（平文保存不可） |
| `family_id`  | VARCHAR(36)  | Token Family（UUID、盗難検知用） |
| `is_revoked` | BOOLEAN      | 無効化フラグ                     |
| `expires_at` | TIMESTAMP    | 有効期限（24 時間）              |
| `created_at` | TIMESTAMP    | 発行日時                         |

**`temp_tokens` テーブル** — WebView ログインの一時 Token 管理:

| カラム       | 型           | 説明                 |
| ------------ | ------------ | -------------------- |
| `id`         | BIGINT PK    | 主キー               |
| `token`      | VARCHAR(36)  | UUID                 |
| `user_id`    | VARCHAR(100) | 認証済みユーザー     |
| `is_used`    | BOOLEAN      | ワンタイム使用フラグ |
| `expires_at` | TIMESTAMP    | 有効期限（30 秒）    |
| `created_at` | TIMESTAMP    | 発行日時             |

**`sso_tickets` テーブル** — SSO Ticket 管理（App → マイページ Web の SSO 連携で使用）:

| カラム       | 型           | 説明                                       |
| ------------ | ------------ | ------------------------------------------ |
| `id`         | BIGINT PK    | 主キー（AUTO_INCREMENT）                   |
| `ticket`     | VARCHAR(36)  | UUID（URL パラメータとしてブラウザに渡す） |
| `user_id`    | VARCHAR(100) | JWT Payload から取得したユーザー識別子     |
| `is_used`    | BOOLEAN      | ワンタイム使用フラグ（DEFAULT: false）     |
| `expires_at` | TIMESTAMP    | 有効期限（発行から 30 秒）                 |
| `created_at` | TIMESTAMP    | 発行日時                                   |

### 5.3 JWT 署名機能

| 項目                 | 内容                                             |
| -------------------- | ------------------------------------------------ |
| **署名アルゴリズム** | RS256（非対称署名）                              |
| **秘密鍵管理**       | Azure Key Vault（HSM-Backed）                    |
| **JWT ライブラリ**   | jjwt (Java)                                      |
| **Payload 要素**     | `sub`(user_id), `iat`(発行日時), `exp`(有効期限) |

### 5.4 Refresh Token Rotation 対応

| 処理               | 内容                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| **発行**           | ログイン成功時に AT + RT を発行、RT ハッシュを DB 保存                       |
| **リフレッシュ**   | 旧 RT を `is_revoked=true` → 新 AT + 新 RT 発行                              |
| **盗難検知**       | `is_revoked=true` の RT が使用された場合 → `family_id` 単位で全 Token 無効化 |
| **クリーンアップ** | `@Scheduled` で 1 日 1 回、期限切れレコード削除                              |

### 5.5 定期バッチ処理

```sql
-- 日次クリーンアップ（期限切れ Token 削除）
DELETE FROM refresh_tokens WHERE expires_at < NOW();
DELETE FROM temp_tokens WHERE expires_at < NOW();
DELETE FROM sso_tickets WHERE expires_at < NOW();
```

## 6. Q&A（澄清式問答）

### Q1: Access Token はサーバー側に保存しないのか？

**A**: 保存不要。Access Token は JWT（自己完結型トークン）であり、Payload にユーザー情報・有効期限が含まれ、RS256 署名で改ざん防止されている。サーバーは署名検証 + 有効期限チェックのみで認証が完了し、DB 照会は不要。

ただし、ログアウトや強制無効化に対応するため、**JWT ブラックリスト**（Redis, TTL: 24h）で無効化された Token のハッシュを管理する。

| Token         | サーバー保存 | 理由                                        |
| ------------- | ------------ | ------------------------------------------- |
| Access Token  | 不要         | JWT の署名検証で完結（stateless）           |
| Refresh Token | **必要**     | Rotation / Reuse Detection に状態管理が必須 |
| tempToken     | **必要**     | ワンタイム使用のため、使用済みフラグが必要  |
| SSO Ticket    | **必要**     | ワンタイム使用のため、使用後に即時削除      |

### Q2: JWT ブラックリストとは何か？

**A**: JWT は本来 stateless であり、一度発行すると有効期限まで無効化できない。JWT ブラックリストは、無効化が必要な Token のハッシュを Redis に保存し、リクエスト時に照会する仕組み。

使用シーン:

- ユーザーがログアウトした場合
- 管理者がユーザーを強制無効化した場合
- Refresh Token 盗難検知時（family 全体の AT を無効化）
- パスワード変更時（全セッション無効化）

```
リクエスト → JWT 署名検証 ✓ → 有効期限 ✓ → Redis ブラックリスト照会
                                              ├→ 存在しない → 認証通過 ✓
                                              └→ 存在する → 401 Unauthorized ✗
```

### Q3: マイページ API に Redis がないのに、Refresh Token をどう管理するのか？

**A**: マイページ DB の `refresh_tokens` テーブルで管理する。Redis と DB の違いは以下の通り:

| 項目         | Redis（CMS API 用）         | DB テーブル（マイページ用）    |
| ------------ | --------------------------- | ------------------------------ |
| アクセス速度 | 高速（< 1ms）               | やや遅い（1–5ms）              |
| TTL 自動削除 | ✅ あり                     | ❌ なし（バッチで手動削除）    |
| 適する用途   | 高頻度の読み書き            | 低〜中頻度の読み書き           |
| 採用理由     | CMS API は既に Redis を利用 | マイページ API に Redis がない |

Mobile App の Token リフレッシュ頻度は 1 時間に 1 回程度であるため、DB 照会のパフォーマンスで十分。

### Q4: CMS API は、マイページ API が署名した JWT をどうやって検証するのか？

**A**: RS256（非対称署名）の公開鍵を Azure Key Vault から取得して検証する。

```
1. CMS API 起動時: Key Vault から RS256 公開鍵を取得してメモリにキャッシュ
2. リクエスト受信時: キャッシュ済み公開鍵で JWT 署名を検証
3. 鍵ローテーション時: Key Vault の鍵を更新 → CMS API を再デプロイ
```

CMS API は秘密鍵にアクセスできないため、JWT の偽造は不可能。

### Q5: CMS 管理画面の JWT 署名が HS256 で、Mobile App 用が RS256 なのはなぜか？

**A**: 署名と検証を行うシステムが同一か否かで使い分ける。

| 状況                   | 署名者 = 検証者？  | 適切な方式 |
| ---------------------- | ------------------ | ---------- |
| CMS 管理画面 → CMS API | ✅ 同一（CMS API） | HS256      |
| Mobile App → CMS API   | ❌ 異なる          | RS256      |

HS256 は共通鍵方式であり、同一システム内で閉じる場合はシンプルで高速。RS256 は異なるシステム間で署名権限を分離する必要がある場合に使用する。

### Q6: パスワード変更時、App のログイン状態はどうなるか？

**A**: セキュリティ上、パスワード変更時にはマイページ API が当該ユーザーの**全 Refresh Token を `family_id` 単位で一括無効化**する。

```
ユーザーがマイページ Web でパスワード変更:
  1. マイページ API: パスワード更新
  2. マイページ API: refresh_tokens テーブルで当該 user_id の全レコードを is_revoked=true
  3. CMS API: JWT ブラックリストに当該ユーザーの AT ハッシュを追加（任意）

App 側:
  4. 次回 API アクセス時（AT 期限切れ後）→ refresh 要求
  5. RT が無効化済み → 401 エラー
  6. ログイン画面に遷移
  7. 旧パスワードの Keychain 情報では生体認証ログイン不可
     （マイページ API でパスワード照合が通らないため）
  8. ユーザーは新パスワードで WebView ログインが必要
  9. ログイン成功後、新 Token が Keychain に保存 → 生体認証復帰
```

影響まとめ:

| 項目                      | 影響                                         |
| ------------------------- | -------------------------------------------- |
| App の Access Token       | AT 期限切れまでは使用可能（最大 1h）         |
| App の Refresh Token      | 即時無効化                                   |
| 生体認証                  | 一時的に使用不可（新 PW でログイン後に復帰） |
| マイページ Web の Session | 影響なし（Session は独立管理）               |
| CMS 管理画面              | 影響なし（CMS ユーザーは別管理）             |

### Q7: 生体認証データはサーバーに送信されるのか？

**A**: **一切送信されない。** 生体認証データ（指紋テンプレート・顔の数学モデル）は、端末内のセキュリティハードウェア（iOS: Secure Enclave / Android: TEE）にのみ保存される。

App → OS: 「ユーザーを認証してください」
OS → ユーザー: 生体認証画面を表示
OS → App: 「認証成功」/「認証失敗」のみ返答

App が受け取るのは認証の成功/失敗のみであり、生体データそのものには一切アクセスできない。生体認証は Keychain/Keystore のロック解除手段であり、サーバーとの通信には関与しない。

### Q8: Keychain (iOS) と Keystore (Android) は同じものか？

**A**: 名称と実装は異なるが、役割は同等。

| 項目                 | Keychain (iOS)                           | Keystore (Android) |
| -------------------- | ---------------------------------------- | ------------------ |
| **OS**               | iOS                                      | Android            |
| **安全ハードウェア** | Secure Enclave                           | TEE / StrongBox    |
| **暗号化**           | AES-256                                  | AES-256            |
| **生体認証連携**     | Face ID / Touch ID                       | BiometricPrompt    |
| **React Native**     | react-native-keychain で統一的にアクセス | 同左               |

開発者は `react-native-keychain` ライブラリを使用することで、両プラットフォームを統一コードで扱える。
